# QuantumShield viva questions and concise answers

These answers describe the implemented research prototype, not production certification. For measurements, use [RESULTS_SUMMARY.md](RESULTS_SUMMARY.md) and disclose the single-machine synthetic scope.

1. **What is QuantumShield's contribution?** A working integration of versioned crypto suites, explainable metadata-based security selection, file sharing, signatures, revocation, and paired measurements. It does not introduce a new primitive.
2. **Why encrypt a file with AES-256-GCM instead of ML-KEM?** AES-GCM encrypts and authenticates file content; ML-KEM establishes a shared secret used to derive a key-encryption key (KEK) for wrapping the file key. ML-KEM is not a bulk-file cipher.
3. **Why use one ciphertext with several envelopes?** Each recipient receives an independently encapsulated and wrapped copy of the same random file key. Sharing does not duplicate or re-encrypt the whole file.
4. **What does HKDF-SHA256 do?** It derives a purpose-bound 32-byte KEK from KEM (and, in hybrid mode, classical) shared material with versioned context and salt. It is not password hashing.
5. **What makes hybrid mode hybrid?** A versioned envelope requires both ML-KEM and ephemeral X25519 contributions, combined through the specified HKDF construction. Both parts must validate; failure does not fall back to PQ-only.
6. **What security levels exist?** LOW maps to ML-KEM-512, STANDARD to ML-KEM-768, and HIGH to ML-KEM-1024. The architecture choice independently selects PQ_ONLY or HYBRID, yielding six approved confidentiality suites.
7. **Is the adaptive selector machine learning?** No. `adaptive-v1` is a deterministic rules engine over explicit sensitivity, category, and secret-bearing extension metadata. It does not inspect content.
8. **Can a user choose weaker protection than policy requires?** RECOMMEND confirmation rejects a lower level; AUTO chooses the policy result and rejects a conflicting explicit level. MANUAL is a separately recorded choice, subject to its documented server constraints.
9. **Why store suite and key versions?** Historical decryption must use the precise algorithm, format, and user key that protected the artifact. A new default must not silently reinterpret old ciphertext.
10. **How is sender authenticity checked?** Separate ML-DSA signing keys sign canonical FILE and SHARE payloads. Download verifies the relevant signature and actual ciphertext digest before decryption. AES-GCM separately authenticates encrypted content.
11. **What does `LEGACY_UNSIGNED` mean?** A pre-signature artifact lacks the new signature requirement and is handled through an explicit compatibility path; it must not be displayed as cryptographically signed.
12. **What does revocation achieve?** It atomically disables an active application share/envelope and blocks future authorized recipient downloads. It cannot erase plaintext or key material already obtained by the recipient.
13. **Is the system end-to-end encrypted or zero-knowledge?** No. The backend manages protected private keys and can recover file plaintext using the application master key. Backend and master-key compromise remain central risks.
14. **What is the main database/storage boundary?** PostgreSQL holds users, authorization, key and envelope metadata, signatures, and audit events. Encrypted file objects are stored separately behind a storage service. Neither location is intended to contain plaintext file contents at rest.
15. **How are file tampering and metadata tampering detected?** AES-GCM authenticates ciphertext/AAD; versioned envelope validation rejects inconsistent algorithm or key metadata; signatures bind canonical package fields and ciphertext digest. Each mechanism addresses a different boundary.
16. **How were performance results obtained?** Offline deterministic synthetic workloads, five warmups and 20 measured iterations for the standard Phase 13 benchmark; the Phase 14 adaptive comparison has 24 scenarios with 30 measured pairs each. Neither includes live HTTP, database, TLS, or real network latency.
17. **What do the Phase 14 savings mean?** In that specific equal-scenario-weight synthetic run, adaptive mean crypto time was 38.565 ms versus 39.931 ms for fixed HIGH (3.422% observed difference), and aggregate metadata was 545,514 versus 568,234 bytes (3.998%). They are observations, not a universal speedup or statistical significance claim.
18. **Why do HIGH scenarios have no designed size saving?** Policy already chooses HIGH, so adaptive and fixed-HIGH use the same suite. Any small time difference there is measurement variation/order effect, not a weaker algorithm.
19. **What did security testing establish?** The controlled Phase 16 suite exercised access control, tamper, malformed inputs, lifecycle, and safe-error behavior and passed 88 cases in this environment. It does not replace a professional penetration test, formal proof, or production operational review.
20. **What would be needed before deployment?** Independent cryptographic review, replacement/reassessment of the beta ML-KEM-512 provider, TLS and abuse controls, KMS/HSM-backed master-key lifecycle, backup/restore rehearsal, and PostgreSQL/HTTP load and concurrency testing.
